# UI 文案优化工具：阶段 1 需求说明

## 1. 文档目的

本文档用于明确阶段 1 的需求背景、产品定位、核心功能、业务流程、功能边界和初步技术路径。

阶段 1 采用“先跑通，再评估准确率”的原则，不追求完整的编辑、管理和协作能力，优先验证以下核心假设：

> 系统能否通过 UI 截图理解页面语境，减少设计师描述复杂业务背景的成本，并生成适合当前界面、业务含义和产品调性的 UI 文案。

## 2. 需求背景

在智能安防等复杂 B 端产品中，设计师经常需要处理功能说明、系统状态、操作结果、异常提示、风险提示、确认弹窗、技术限制和免责声明等文案。

这类文案通常具有以下特点：

- 与具体业务场景强相关；
- 需要同时包含状态、原因、影响、限制和下一步操作等多类信息；
- 涉及系统能力、技术限制或操作后果；
- 需要避免用户无法理解的专业术语；
- 受到弹窗、提示框等界面空间限制；
- 精简后仍然不能改变业务事实。

目前使用通用 AI 优化这类文案时，设计师需要反复说明系统背景、页面用途、业务场景、触发条件、技术限制和用户影响。真正耗时的不是输入原文，而是重复构造上下文。

UI 截图本身已经包含系统名称、模块、页面标题、操作入口、状态、相邻文案和现有语言风格等信息。本工具希望让 AI 先从截图获得主要上下文，只在关键信息缺失时要求用户进行有针对性的补充。

## 3. 产品定位

本产品是一个面向 UI 设计师和产品设计师的轻量网页工具。

用户上传 UI 截图后，系统结合 OCR 和视觉大模型能力：

1. 识别截图中的文字及其位置；
2. 理解页面所属系统、页面类型、核心任务和当前状态；
3. 区分需要优化的业务文案与不应修改的数据内容；
4. 根据用户要求或自动匹配的文案风格生成优化结果；
5. 将优化结果展示在原文字所在位置附近；
6. 允许用户调整条件后重新生成。

本产品不是通用 OCR、错别字检查或普通文字批量润色工具。其核心能力是：

> 页面语境理解、UI 文案角色识别和受业务约束的文案生成。

## 4. 目标用户与典型场景

### 4.1 目标用户

- UI 设计师
- 产品设计师

### 4.2 典型场景

- 为复杂状态设计提示语；
- 编写包含多个必要条件的弹窗说明；
- 将技术限制转换为客户能够理解的表达；
- 在有限界面空间内压缩功能说明；
- 在不改变事实的前提下优化风险提示或免责声明；
- 让新增文案符合当前系统已有的风格和调性。

## 5. 文案对象范围

### 5.1 UI 固定文案

UI 固定文案是由产品预先设计、由系统固定展示给用户的文字，而不是运行过程中产生的业务数据，例如页面标题、按钮、字段标签、弹窗标题、功能说明和状态提示。

但“UI 固定文案”仍然过于宽泛。阶段 1 真正关注的是其中的“业务说明型文案”。

### 5.2 业务说明型文案

业务说明型文案主要包括：

- 向用户解释当前状态的文案；
- 说明功能用途或能力边界的文案；
- 告知操作影响和后果的文案；
- 解释异常原因并提供下一步操作的文案；
- 涉及业务规则、技术限制和风险说明的文案。

### 5.3 默认处理范围

| 内容类别 | 示例 | 阶段 1 默认处理策略 |
| --- | --- | --- |
| 操作提示 | 删除后无法恢复，是否继续？ | 优化 |
| 状态说明 | 设备离线，实时预览暂不可用 | 优化 |
| 功能说明 | 开启后将自动检测区域入侵事件 | 优化 |
| 风险或限制说明 | 受网络环境影响，结果可能存在延迟 | 优化 |
| 操作按钮 | 确认删除、重新连接 | 不优化 |
| 页面标题、字段标签 | 设备管理、设备名称 | 不优先 |
| 动态业务数据 | 设备 A、192.168.1.1、离线 3 小时 | 不优化 |
| 用户输入内容 | 用户填写的名称、备注 | 不优化 |
| 时间、编号、统计值 | 2026-08-16、告警 23 条 | 不优化 |
| 产品或技术专有名词 | 产品名、算法名、协议名 | 不优化 |
| 导航和菜单 | 首页、配置中心、系统管理 | 不优先 |

系统无法确定内容类型时，应采用保守策略：不直接改写，并在内部标记为不确定。

## 6. 产品原则

### 6.1 先理解页面，再优化文案

系统不能将 OCR 结果作为互不相关的文字逐条润色。正确处理顺序是：

```text
页面整体理解
→ 文字和界面结构识别
→ 文案类型判断
→ 业务说明型文案筛选
→ 结合上下文生成文案
```

### 6.2 不改变业务事实

系统不得为了表达更顺畅而自行添加或改变功能能力、技术原因、系统状态、操作结果、风险范围、责任边界或解决方式。

### 6.3 信息不足时明确追问

当截图不能支持可靠生成时，系统不得猜测，应说明：

- 缺少什么信息；
- 该信息为什么影响文案；
- 用户具体需要补充哪些内容。

一次最多询问三个关键问题，尽可能降低用户负担。

### 6.4 自动匹配风格，但保持透明

用户不填写风格时，系统自动匹配，并用一句话说明生成依据。例如：

> 根据当前页面的系统状态提示场景，本次采用“严谨、简洁、弱化专业术语，并提供下一步操作”的文案风格。

用户可以调整风格后重新生成。

### 6.5 阶段 1 采用低成本试错

阶段 1 不建设复杂编辑能力。结果不满意时，用户可以调整风格、补充背景并重新生成整组结果。

## 7. 核心业务流程

```text
进入网页
  ↓
上传一张 UI 截图
  ↓
OCR 识别文字及位置
  ↓
AI 理解页面业务和界面结构
  ↓
系统展示页面理解摘要与自动风格依据
  ↓
判断现有信息是否足够
  ├─ 信息不足 → 要求用户补充明确的业务信息
  └─ 信息足够 → 继续
  ↓
自动筛选业务说明型文案
  ↓
用户选择或调整文案风格（可不操作）
  ↓
生成优化结果
  ↓
在原文字位置附近展示结果
  ↓
用户判断结果
  ├─ 满意 → 结束
  └─ 不满意 → 调整风格/补充背景/重新生成
```

## 8. 阶段 1 功能需求

### 8.1 图片上传与预览

- 支持点击或拖拽上传一张 JPG、JPEG 或 PNG 图片；
- 展示真实图片预览；
- 支持更换当前图片；
- 检查文件格式、大小和基本清晰度；
- 图片不符合要求时说明具体原因。

阶段 1 不支持多图上传。

### 8.2 OCR 文字识别

系统需要输出：

- 识别文字；
- 文字在截图中的坐标；
- OCR 置信度；
- 文本块之间的空间关系。

系统应尽量将属于同一语义块的多行文字合并，避免把一段说明拆成多个无关结果。

### 8.3 页面语境理解

系统结合截图和 OCR 结果判断：

- 可能是什么类型的系统；
- 当前页面或功能模块；
- 页面核心功能；
- 用户当前任务；
- 页面状态及组件结构；
- 当前语言风格；
- 文案之间的上下文关系。

系统输出一段简短的页面理解摘要，供用户判断理解是否正确。

阶段 1 提供以下操作：

- 理解正确，继续；
- 理解不准确，重新分析；
- 补充业务背景。

阶段 1 暂不提供直接编辑理解摘要的能力。

### 8.4 信息充分性判断与补充

信息足够时，系统直接进入生成准备状态。

信息不足时，系统需要：

- 说明无法确定的业务点；
- 说明其对文案准确性的影响；
- 提出最多三个具体问题；
- 提供统一的补充输入区域；
- 用户提交后重新进行页面理解和充分性判断。

### 8.5 文案对象筛选

系统自动将 OCR 内容划分为：

- 业务说明型文案；
- 普通 UI 标签；
- 动态业务数据；
- 专有名称；
- 无法确定。

阶段 1 默认只优化业务说明型文案，不提供复杂的手动分类界面。

### 8.6 风格匹配与调整

阶段 1 提供以下风格：

- 自动匹配（系统根据页面语境，从以下四种风格中选择一种）；
- 极致精简；
- 去专业化；
- 严谨说明；
- 友好引导。

第一版只允许选择一个主要风格，避免规则叠加冲突。用户也可以输入一段补充要求。

自动匹配时，系统展示选定风格和一句话依据。

### 8.7 文案生成

系统针对每条目标文案，综合以下信息生成结果：

- 页面整体语境；
- 原文及其界面位置；
- 相邻文字；
- 文案类型；
- 用户补充的业务信息；
- 当前风格；
- 文字所在区域的空间限制。

输出至少包含：

- 原文；
- 优化文案；
- 对应截图位置；
- 信息风险状态。

系统内部保留生成判断依据，但阶段 1 暂不强制展示详细优化理由。

### 8.8 原位结果展示

- 在截图中标出被优化文案的位置；
- 在对应位置附近展示优化结果；
- 支持切换查看原文和优化结果；
- 长文案可通过浮层或侧边区域完整展示。

阶段 1 不进行图片原文擦除和高保真重绘，使用覆盖层、定位框或浮层建立位置对应关系。

### 8.9 重新生成

用户可以：

- 使用相同条件重新生成全部结果；
- 切换风格后重新生成；
- 补充业务信息后重新生成。

## 9. 页面状态

整个流程由一个网页承载，不设计复杂的多页面路由。

### 9.1 初始状态

- 图片上传入口；
- 支持格式说明；
- 风格选择；
- 补充要求；
- 上传前生成按钮不可用。

### 9.2 识别与理解状态

- 展示图片预览；
- 展示 OCR 识别区域；
- 分阶段显示“识别文字、理解页面、筛选文案”等进度。

### 9.3 理解确认或信息补充状态

- 页面理解摘要；
- 自动匹配的风格及依据；
- 必要的补充问题；
- 补充输入区域；
- 继续生成操作。

### 9.4 结果状态

- 截图及文案位置标记；
- 原文和优化结果切换；
- 当前页面理解与风格；
- 调整风格；
- 补充业务信息；
- 重新生成全部结果。

## 10. 阶段 1 不包含

- 登录、账号及权限；
- 历史记录和云端任务管理；
- 多图片批量处理；
- 团队协作；
- 手动编辑文案；
- 单条重新生成；
- 采纳、拒绝及版本管理；
- 一键复制和结果导出；
- 设计规范库和品牌语言库；
- Figma 插件；
- 自动替换设计稿内容；
- 截图文字的高保真擦除和重绘；
- 多语言翻译。

## 11. 初步技术路径

### 11.1 前端

继续使用现有 Next.js 网页项目，在单一工作台中通过状态切换完成上传、识别、理解确认、信息补充、生成和结果展示。

前端主要负责图片上传与预览、截图坐标映射、OCR 框展示、表单输入、处理状态、原文/结果切换和重新生成。

### 11.2 OCR

阶段 1 优先使用成熟的第三方 OCR 服务，重点评估中文 UI 小字号识别、多行文本合并、坐标输出、速度和成本。暂不自行训练 OCR 模型。

### 11.3 页面理解

将原始截图和 OCR 结构化结果交给支持视觉理解的大模型，要求其输出结构化的页面摘要、业务领域推断、页面类型、核心任务、文案分类、风格判断和信息缺口。

### 11.4 文案生成

在页面理解完成后，再根据页面上下文、目标文案、用户补充信息和风格要求生成结构化结果。

产品逻辑上将“页面理解”和“文案生成”拆成两个阶段，以便识别错误来源、触发必要追问并提高可控性。实际服务调用次数可根据模型能力、延迟和成本再决定。

### 11.5 服务端

使用 Next.js 服务端接口完成图片接收、OCR 调用、视觉模型调用、提示词编排、模型结果校验和统一错误处理，避免在浏览器暴露服务密钥。

阶段 1 不使用数据库，任务状态暂存在当前页面会话中，刷新后清空。

## 12. 验收标准

### 12.1 流程验收

- 能上传并预览一张有效 UI 截图；
- 能识别截图文字及位置；
- 能输出页面理解摘要；
- 能展示自动风格及其依据；
- 信息不足时能提出明确补充问题；
- 能排除明显的动态数据；
- 能针对业务说明型文案生成优化结果；
- 结果与截图原文字位置存在清晰对应；
- 能切换风格或补充信息并重新生成。

### 12.2 基础质量约束

- 不随意修改时间、编号、设备名称等动态数据；
- 不虚构已有信息之外的业务事实；
- 保持原文的核心业务含义；
- 去专业化后仍保留必要信息；
- 结果基本符合 UI 空间和使用场景；
- 无法确认的关键信息必须追问或提示风险。

## 13. 阶段 1 验证重点

阶段 1 先验证链路可用，再通过测试样本评估准确率。重点记录：

1. 页面理解是否正确；
2. 业务说明型文案筛选是否准确；
3. 动态数据是否被错误优化；
4. 用户还需要补充多少背景；
5. 结果是否保持业务含义；
6. 平均重新生成多少次能够获得可用结果；
7. 相比直接使用通用 AI，是否明显减少输入和沟通成本。

阶段 1 的成功标准是：

> 在不输入大段业务背景的情况下，设计师能够通过一张截图和少量补充信息，获得至少一版业务含义正确、表达简洁且可用于 UI 的文案。

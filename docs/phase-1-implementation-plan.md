# UI 文案优化工具：阶段 1 实现计划

> 动态交互、状态流转与验收规则以 [phase-1-interaction-design.md](./phase-1-interaction-design.md) 为准；视觉以最终 Figma 六个页面节点为准。

## 1. 实施目标

按照“先跑通端到端流程，再评估和提升准确率”的顺序，完成以下最小闭环：

```text
上传截图
→ OCR 识别文字及坐标
→ 大模型理解页面并筛选目标文案
→ 信息不足时提出补充问题
→ 自动匹配或用户选择文案风格
→ 大模型生成优化结果
→ 在截图原位置附近展示
→ 用户调整条件并重新生成
```

阶段 1 的 UI 设计由用户通过 Figma 提供；其余技术方案、代码实现、服务接入、联调、测试和问题修复由开发执行，完成后交由用户审核。

## 2. 实施原则

- 优先跑通真实服务链路，不先投入复杂准确率优化；
- 产品流程保持单页面工具形态；
- 页面理解和文案生成在产品逻辑上分层；
- 所有模型输出采用结构化协议并在服务端校验；
- 不确定业务事实时追问，不允许模型自行补全；
- 先使用第三方成熟能力，不训练自有 OCR 或大模型；
- 阶段 1 不建设账号、数据库和历史记录；
- 在不影响主链路的前提下，避免提前实现编辑、复制、导出等能力。

## 3. 前置输入与待确认项

### 3.1 用户提供

- 阶段 1 Figma 页面链接；
- 页面各状态对应的设计稿或状态说明；
- 如有：组件状态、响应式规则和交互备注；
- 用于联调和验收的典型 UI 截图样本，建议至少 5 张。

### 3.2 开发侧确认

- OCR 服务选型；
- 视觉大模型及文案生成模型选型；
- 服务调用凭证和环境变量；
- 图片大小、格式和超时限制；
- 请求失败、模型拒绝和结构化结果异常时的降级策略。

## 4. 技术架构草案

### 4.1 前端

- 基于现有 Next.js、React、TypeScript 和 Tailwind CSS；
- 单页工作台，通过状态机管理完整流程；
- 图片预览层负责坐标缩放和识别框定位；
- 所有模型及 OCR 请求只通过服务端接口发起。

### 4.2 服务端接口

建议按产品阶段拆分为两个主接口：

1. `POST /api/analyze`
   - 接收图片和可选的用户补充信息；
   - 调用 OCR；
   - 调用视觉模型进行页面理解、文案分类和信息充分性判断；
   - 返回页面摘要、自动风格、补充问题及 OCR 文本块。

2. `POST /api/generate`
   - 接收页面分析结果、目标文案、用户补充信息和风格；
   - 生成结构化优化结果；
   - 返回原文、优化文案、位置及风险状态。

阶段 1 不使用数据库。图片和结果仅在当前请求及浏览器会话中使用。

### 4.3 核心数据对象

需要在开发开始时确定以下 TypeScript 数据结构：

- 上传图片元数据；
- OCR 文本块和归一化坐标；
- 页面理解结果；
- 文案类别；
- 信息缺口和补充问题；
- 文案风格；
- 文案生成结果；
- 页面流程状态和接口错误。

坐标统一使用相对于原图宽高的归一化值，避免不同屏幕尺寸和截图缩放导致定位偏移。

## 5. 实施阶段

### 里程碑 0：工程基线与协议设计

目标：建立可稳定开发的项目基础，并锁定前后端数据协议。

工作内容：

- 修复当前依赖安装或构建异常；
- 补充依赖锁文件，固定依赖版本；
- 整理未使用的历史演示组件，暂不做破坏性删除；
- 增加环境变量示例和服务配置说明；
- 定义核心 TypeScript 类型；
- 定义分析、生成和错误响应协议；
- 建立基本的格式检查、类型检查和构建验证方式；
- 准备一组本地假数据，支持无外部服务时开发 UI 流程。

交付结果：

- 项目可以稳定安装和构建；
- 前后端协议明确；
- 使用假数据可以模拟完整流程状态。

### 里程碑 1：单页流程骨架

目标：先用假数据跑通产品状态流转。

工作内容：

- 建立明确的页面状态机；
- 实现图片上传、格式校验、更换和真实预览；
- 实现初始、分析中、信息补充、生成中、结果和失败状态；
- 实现风格选择与补充要求输入；
- 实现重新分析和重新生成操作；
- 使用假 OCR 和假模型数据验证完整交互。

依赖：

- Figma 设计稿可在本里程碑开始前或进行中提供；
- Figma 未提供前先完成功能骨架，提供后再进行视觉实现。

交付结果：

- 不依赖真实 AI 服务即可完整走通阶段 1 流程。

### 里程碑 2：OCR 接入

目标：实现真实截图文字识别和位置返回。

工作内容：

- 调研并确定 OCR 服务；
- 建立服务端 OCR 适配层；
- 实现图片大小、格式和超时控制；
- 将服务商坐标转换为统一归一化坐标；
- 实现多行文本块的基础合并；
- 在图片上展示识别框；
- 处理未识别到文字、低置信度和服务失败等情况。

交付结果：

- 上传真实 UI 截图后，可以获得文字、坐标和置信度并正确定位。

### 里程碑 3：页面理解与必要追问

目标：让系统先理解页面，再决定哪些文案需要优化。

工作内容：

- 设计页面理解提示词；
- 将原图和 OCR 结果共同发送给视觉模型；
- 输出页面类型、核心功能、用户任务、页面状态和语言风格；
- 将 OCR 内容分类为业务说明型文案、普通标签、动态数据、专有名称和不确定内容；
- 判断信息是否足够；
- 信息不足时输出最多三个具体补充问题；
- 增加结构化输出校验、重试和安全降级；
- 在前端展示页面摘要、自动风格及其依据。

交付结果：

- 系统可以输出可读的页面理解摘要；
- 可以自动筛选候选文案；
- 信息不足时不会直接编造，而是要求用户补充。

### 里程碑 4：文案生成

目标：基于页面理解和业务约束生成结构化优化文案。

工作内容：

- 设计文案生成提示词和系统约束；
- 将页面摘要、目标文案、相邻文案、位置、用户补充信息和风格作为输入；
- 实现自动匹配、极致精简、去专业化、严谨说明和友好引导五种风格；
- 输出原文、优化文案、来源坐标和信息风险；
- 防止模型返回未识别的文本对象或修改动态数据；
- 支持相同条件、调整风格和补充背景后的整组重新生成；
- 处理超时、部分结果缺失和结构异常。

交付结果：

- 真实截图可以获得与原始文字区域对应的文案优化结果。

### 里程碑 5：Figma UI 接入与原位展示

目标：按照用户提供的 Figma 完成阶段 1 界面，并实现可审核的原位结果体验。

工作内容：

- 分析 Figma 页面、组件、Token 和状态；
- 将现有页面调整为 Figma 对应结构；
- 实现截图缩放与定位框同步；
- 实现原文/优化结果切换；
- 处理长文案、重叠识别框和小尺寸区域；
- 完善响应式布局、键盘焦点和基础可访问性；
- 补齐加载、空状态、错误和重试状态；
- 根据审核反馈迭代视觉与交互。

交付结果：

- 阶段 1 全部流程与 Figma 设计一致；
- 用户能够直观看到优化文案和原始位置的对应关系。

### 里程碑 6：端到端验收与交付

目标：确认主链路稳定可用，形成第一版准确率评估基础。

工作内容：

- 使用典型业务截图完成端到端测试；
- 覆盖有效图片、无文字、模糊图片、服务超时、信息不足和结构异常；
- 检查动态数据是否被误改；
- 检查页面理解和文案结果是否保留业务事实；
- 记录每个测试样本的模型输入、结构化输出和人工评价；
- 修复阻断流程的问题；
- 补充本地运行、环境变量和服务配置文档；
- 向用户提交可运行版本进行审核。

交付结果：

- 阶段 1 主链路稳定跑通；
- 有一组可用于下一阶段准确率分析的测试记录；
- 用户可以开始进行业务审核。

## 6. UX 与交互实现规格

本节记录不需要在 Figma 主流程页面中逐一表达、但阶段 1 开发必须实现并验收的动态交互规则。实现应以最终 Figma 视觉稿为准，同时遵守以下行为约束。

### 6.1 画布缩放与平移

- 在左侧画布底部增加独立缩放工具条，推荐位于画布左下角，与底部中央任务工具条处于同一水平线；
- 工具条提供“进入/退出全屏、缩小、当前比例、放大、100%”操作，第一个按钮为全屏切换；
- 普通模式使用一个连续的底部工具坞，并按亲密性分为两组：“待优化数量、重新识别、上传图片”作为当前图片任务组；“全屏、缩小、比例、放大、100%”作为画布视图组；两组之间使用分隔线和更大间距；
- “适应画布”作为比例菜单选项和键盘快捷操作提供，不占用独立按钮；
- 支持鼠标滚轮或触控板缩放；
- 支持按住空格拖动画布，也可在非交互区域直接拖动；
- 支持双击高亮文案进行局部放大；
- 缩放以指针所在位置或画布中心为基准，避免每次缩放后丢失当前关注区域；
- 切换图片、重新识别后默认恢复为“适应画布”；
- OCR 坐标统一使用相对于原图宽高的归一化坐标，缩放和平移后高亮区域必须与原图文字保持对齐；
- 高亮文案的实际点击热区不小于 32px，视觉框可以继续保持原始文字区域尺寸；
- 缩放按钮的实际点击热区不小于 44×44px，并提供明确的键盘焦点样式；
- 键盘应支持 `+`、`-`、`0` 适应画布和 `Esc` 退出全屏，输入框聚焦时不得触发画布快捷键；
- 进入全屏后隐藏品牌、右侧设置面板和底部任务工具条，只保留截图、高亮结果、缩放工具和轻量结果计数；
- 全屏画布使用深炭灰背景，截图保持原色、等比居中且不得裁切，四周预留安全边距；
- 全屏状态下底部工具坞中的全屏按钮切换为“退出全屏”，右上角同时提供明确的“退出全屏”入口；
- 全屏模式的底部工具坞精简为“已优化数量｜退出全屏、缩小、比例、放大、100%”，不显示重新识别和上传图片；
- 全屏和退出全屏时保持当前缩放比例、平移位置及正在查看的文案状态，不得重新载入或重新分析图片。

### 6.2 分析进度与取消

- 分析期间使用 Figma 定义的全页面遮罩并锁定其他操作；
- 同一个加载组件依次显示“正在识别界面文字、正在理解页面内容、正在筛选需要优化的文案、正在判断业务信息是否充分”；
- 文案按实际阶段切换，不使用与真实进度无关的虚假百分比；
- 进度状态使用 `role="status"` 或等价的可访问语义，并通过 `aria-live="polite"` 仅播报阶段变化；
- 尊重 `prefers-reduced-motion`，减少动态效果时使用静态进度符号，不持续旋转；
- 点击取消后停止当前分析请求，保留已上传图片，并提示“已停止分析，图片已保留”；
- 取消后提供“继续分析”和“重新上传”入口，不返回无图片的初始化状态。

### 6.3 参与优化内容的表达

- 阶段 1 只区分“参与优化”和“不参与优化”两类内容；
- 参与优化内容使用 Figma 定义的蓝色虚线框；
- 不参与优化内容不显示识别框，也不显示额外分类；
- “待优化：N”只统计参与优化的业务说明型文案，不统计全部 OCR 文本；
- 蓝色框不能成为唯一语义来源，底部计数和必要的状态提示应同步说明当前处于待优化状态。

### 6.4 优化结果与原文切换

- 优化完成页面默认在原位置展示优化后的文案；
- 优化结果使用半透明蓝色填充高亮，与分析完成时的蓝色虚线框形成明确差异；
- 点击高亮区域后，在同一位置切换显示原文；
- 显示原文时增加轻量“原文”状态标识；
- 再次点击当前高亮区域，或点击其他高亮区域时，恢复显示优化文案；
- 同一时刻最多允许一条文案处于“查看原文”状态；
- 首次进入优化完成状态时显示一次轻提示：“点击高亮文案查看原文”；
- 高亮区域必须可通过 Tab 聚焦，并支持 Enter、Space 切换；
- 使用 `aria-pressed` 或等价状态向辅助技术表达当前是否显示原文；
- 不能只通过颜色表达原文和优化结果状态；
- 完成时短暂显示“已优化 N 条文案”，不使用庆祝动画；
- 优化完成后的底部计数显示“已优化：N”。

### 6.5 补充信息表单

- 系统提出的每个问题必须与对应输入控件一一组合，不使用“问题列表 + 单一通用文本框”；
- 必填问题按照 Figma 设计显示红星标识；
- 文本输入和单选项均使用真实表单标签；单选问题使用 `fieldset`、`legend` 或等价语义分组；
- 所有必填项未完成时，“提交并继续优化”按钮保持禁用；全部完成后直接进入文案生成，不重复执行 OCR；
- “暂不确定”视为有效选择，提交后由系统重新判断信息是否充分；
- 文本只包含空格时视为未填写；
- 字段失焦后再显示具体校验错误，不在页面初始载入时立即报错；
- 提交失败或系统判断信息仍不足时保留用户已填写内容，并更新需要继续补充的问题；
- 提交时按钮进入加载和禁用状态，防止重复提交；
- 错误发生后将键盘焦点移动到第一个无效字段。

### 6.6 风格选择

- 阶段 1 风格保持单选；
- 按 Figma 最终设计使用蓝色描边表达选中状态；
- 实现中同时提供背景、勾选标识或其他非颜色信号，确保选中状态不只依赖颜色；
- 定义默认、悬停、按下、选中、键盘焦点和禁用状态；
- 风格控件实际点击热区不小于 44×44px，视觉尺寸可以保持紧凑；
- “自动匹配”默认选中，系统完成分析后展示实际采用的优化依据。

### 6.7 重新识别、重新上传与重新优化

- 重新识别：保留当前图片和用户补充要求，清空 OCR 结果、页面理解、优化依据和优化结果，然后重新执行图片分析；
- 重新上传：替换当前图片，并清空当前任务的分析、补充信息和优化结果；已有分析或结果时先进行二次确认；
- 重新优化：保留图片、OCR、页面理解和当前设置，只重新执行文案生成；
- 三种操作使用 Tooltip、帮助文字或确认对话框说明影响范围；
- 操作失败时不得清空仍可复用的图片、用户输入和上一次有效结果。

### 6.8 响应式与滚动

- 阶段 1 以桌面端为主，但至少验证 1920×1080、1440×900、1366×768 和 1280×720；
- 验证浏览器 125%、150% 和 200% 缩放；
- 右侧面板内容区域独立滚动，面板标题和底部主按钮保持可见；
- 固定按钮不得遮挡最后一个字段，滚动区底部预留足够空间；
- 页面理解、优化依据、三个补充问题和长输入内容同时出现时布局不能溢出；
- 左侧图片保持等比缩放，不允许拉伸；
- 窄屏下优先保证设置面板和主操作可用，不采用破坏 OCR 坐标的任意裁切；
- 阶段 1 不要求完整手机体验，但不得出现无法操作的横向溢出。

### 6.9 错误与恢复

使用统一错误组件覆盖以下场景：

- 图片格式不支持或超过大小限制；
- 图片过于模糊；
- 未识别到文字；
- OCR 服务失败或超时；
- 页面理解失败；
- 补充信息后仍不足；
- 文案生成失败或结构化结果异常。

每个错误状态必须说明：

1. 哪一个阶段失败；
2. 当前图片、补充信息和已有结果是否保留；
3. 用户应该执行“重新上传、重新分析还是重新优化”；
4. 重试过程中避免重复请求；
5. 错误信息使用用户可理解的语言，不直接暴露服务商错误或技术堆栈。

### 6.10 上传与隐私提示

- 上传区域支持点击和拖拽，并提供明确的拖入反馈；
- 显示支持格式和文件大小上限；
- 图片处理和保存策略确定后，在上传入口附近使用简短、事实准确的隐私提示；
- 不得在技术方案尚未确定时承诺“图片不会上传服务器”或“立即删除”等未经验证的行为。

## 7. 推荐实施顺序

```text
工程基线与协议
→ 假数据单页流程
→ OCR 接入
→ 页面理解与追问
→ 文案生成
→ Figma 视觉接入与原位展示
→ 端到端验收
```

Figma 视觉接入与服务研发可以部分并行，但最终交互状态必须在真实接口接入后再次校准。

## 8. 测试样本建议

首轮至少准备 5 类真实或脱敏截图：

1. 简单确认弹窗；
2. 包含技术限制的功能说明；
3. 包含异常原因和解决方法的状态提示；
4. 同时含大量表格动态数据和少量业务说明的复杂页面；
5. 截图自身无法提供全部业务背景、必须追问的场景。

每张截图应尽量保留一份设计师认可的参考文案，用于后续判断业务事实、可理解性和精简程度，而不是要求模型逐字匹配参考答案。

## 9. 阶段 1 完成定义

满足以下条件后，阶段 1 视为完成：

- 主流程可以通过真实 OCR 和大模型服务端到端运行；
- 用户不输入大段背景也能获得页面理解和候选文案；
- 信息不足时系统能够提出具体问题；
- 系统不会明显地批量改写动态数据；
- 生成结果与截图位置能够正确对应；
- 用户能够调整风格或补充信息后重新生成；
- 关键失败场景有明确提示和重试入口；
- 项目可以稳定安装、构建和本地运行；
- 用户完成 UI 和业务流程审核；
- 画布缩放、平移和 OCR 坐标映射通过多分辨率验证；
- 优化结果与原文切换支持鼠标、触控板和键盘操作；
- 补充信息必填校验、禁用状态和错误恢复符合本实现规格；
- 主要流程在 1280×720 到 1920×1080 及 200% 浏览器缩放下可完成；
- 上传、OCR、理解和生成失败均有明确恢复入口，并保留仍可复用的用户数据。

准确率提升、提示词精调和模型对比不作为“跑通阶段”的阻断条件，但实现过程中发现的准确率问题需要记录并进入后续优化清单。

## 10. 后续阶段候选项

阶段 1 完成并评估准确率后，再决定是否进入以下能力：

- 单条文案重新生成；
- 手动编辑；
- 快捷复制和导出；
- 采纳、拒绝和版本对比；
- 历史记录；
- 多图批量处理；
- 团队规则和品牌语言库；
- Figma 插件或设计稿回填；
- 更细粒度的文案分类和准确率优化。
